- `TuVi_Build_Spec_v1.md` mục 14 — chuẩn UI tối thiểu: "đầy đủ và giống mức độ thông tin hiển
  thị của tuvi.vn (đủ 12 cung, đủ chính/phụ tinh, đủ chú thích miếu vượng đắc hãm, đủ Đại
  Vận/Tiểu Vận/Lưu Niên...) — chưa cần trang trí/hiệu ứng".
- `src/chart/` (Chart Engine, Phase 2) + `src/rule/` (Rule Engine, Phase 3) + `src/server/`
  (API Server, Phase 4) — đã hoàn thành, review sạch, đã push GitHub. UI tiêu thụ 2 endpoint đã
  có (`POST /charts`, `POST /charts/rules`), và mở rộng nhẹ cả hai + Chart Data Shape để đủ dữ
  liệu (mục 2 dưới đây).
- Ảnh lá số gốc tuvi.vn (reference implementation #1, đã dùng xuyên suốt dự án) — dùng làm
  chuẩn đối chiếu bố cục UI, KHÔNG phải chuẩn đối chiếu dữ liệu (dữ liệu vẫn theo nguyên tắc mục
  7 design doc Chart Engine: không ép `iztro` khớp ảnh khi lệch trường phái).

## 2. Nguyên tắc bắt buộc (nhắc lại, áp dụng khi code)

- **Không ép dữ liệu khớp ảnh gốc khi lệch trường phái** (nguyên tắc xuyên suốt từ Chart Engine
  mục 7): UI hiển thị đúng những gì `iztro` tính ra. Nếu 1 sao ở vị trí khác ảnh gốc, đó là dữ
  liệu thật của engine đang dùng, không phải lỗi UI cần "sửa cho đẹp".
- **Không đoán khi không chắc** (bài học lặp lại nhiều lần trong dự án): trường "Th.1" chưa xác
  định → không hiển thị, không bịa.
- **Fail loud**: nếu 1 field cần cho UI mà `iztro`/Chart Engine không cung cấp, throw lỗi rõ
  ràng ở tầng adapter, không hiển thị giá trị rỗng/mặc định âm thầm sai.
- **UI chưa cần đẹp** (build spec mục 14): không CSS framework, không animation, không responsive
  polish — chỉ cần đúng cấu trúc thông tin, đọc được.

## 3. Phần A — Mở rộng Chart Data Shape + API Server

### 3.1. `ChartPalace` — thêm 4 field vòng 12 thần + ngũ hành cung

```ts
export interface ChartPalace {
  // ... các field hiện có (branch, palace_name, palace_stem, is_body_palace,
  //     is_original_palace, major_stars, minor_stars, adjective_stars, sihua) giữ nguyên
  /** Ngu hanh cua chi cung nay (Kim/Moc/Thuy/Hoa/Tho) — bang tinh 12 dia chi,
      lay tu iztro.data.earthlyBranches, khong phai tinh toan rieng cua Chart Engine. */
  branch_element: NguHanh;
  /** Vong Trang Sinh (iztro: changsheng12) — vd "Lam Quan", "De Vuong". */
  truong_sinh: string;
  /** Vong Bac Sy 12 than (iztro: boshi12). */
  boshi: string;
  /** Vong Tuong Tien 12 than (iztro: jiangqian12). */
  jiangqian: string;
  /** Vong Tue Tien 12 than (iztro: suiqian12). */
  suiqian: string;
}
```

**Nguồn dữ liệu đã xác nhận** (đọc trực tiếp `iztro`, không suy đoán):
- `branch_element`: `iztro.data.earthlyBranches[key].fiveElements` (tiếng Trung: 水/木/火/土/金)
  → map sang `NguHanh` đã có (`Thuy`/`Moc`/`Hoa`/`Tho`/`Kim`) qua bảng tra 12 địa chi cố định
  (Tý/Hợi→Thủy, Sửu/Thìn/Mùi/Tuất→Thổ, Dần/Mão→Mộc, Tỵ/Ngọ→Hỏa, Thân/Dậu→Kim — đã đối chiếu
  khớp giữa bảng `iztro` và kiến thức tử vi chuẩn).
- `truong_sinh`/`boshi`/`jiangqian`/`suiqian`: đọc thẳng từ `palace.changsheng12`/`boshi12`/
  `jiangqian12`/`suiqian12` của `iztro` — dữ liệu đã có sẵn từ Phase 2, chỉ chưa được map vào
  `ChartPalace`.

### 3.2. `Chart` — thêm field `luu_nien` optional

```ts
export interface LuuNienPalace {
  branch: Branch;
  /** Ten cung theo Luu Nien (khac ten cung goc — vong Luu Nien xoay theo nam xem). */
  palace_name: string;
  stars: { star_id: string }[];
}

export interface LuuNien {
  year: number;
  heavenly_stem: string;
  earthly_branch: string;
  mutagen: string[];
  palaces: LuuNienPalace[];
}

export interface Chart {
  // ... field hien co giu nguyen
  /** Luu Nien — CHI co khi BuildChartInput kem nam xem. Khong phai fact tinh
      cua la so (phu thuoc nam tra cuu) — xem giai thich da co trong LuckCycles. */
  luu_nien?: LuuNien;
}
```

**`BuildChartInput` thêm field optional:**
```ts
export type BuildChartInput = (
  | { calendar_type: 'duong_lich'; date: string; time_index: number; gender: Gender; fix_leap?: boolean }
  | { calendar_type: 'am_lich'; date: string; time_index: number; gender: Gender; is_leap_month?: boolean; fix_leap?: boolean }
) & {
  /** Nam xem cu the (duong lich, vd "2026-01-01"). Neu co, Chart.luu_nien duoc dien.
      Neu khong co, Chart.luu_nien la undefined — khong loi. */
  view_year?: string;
};
```

**Nguồn dữ liệu:** `astrolabe.horoscope(view_year, 0).yearly` — đã xác nhận có sẵn đầy đủ
(`heavenlyStem`, `earthlyBranch`, `palaceNames` mảng 12 tên cung theo thứ tự lưu niên,
`mutagen`, `stars` mảng lưu tinh từng cung). Khi `view_year` không được cung cấp, `adaptFromIztro`
không gọi `horoscope()`, `luu_nien` là `undefined` trên `Chart` — không lỗi, đúng optional.

### 3.3. Tại sao KHÔNG đưa `luu_nien` vào `ChartPalace` (mà để riêng ở `Chart`)

`LuckCycles` (design doc Chart Engine, đã quyết định trước) giải thích: `luu_nien` phụ thuộc
năm tra cứu, không phải fact tĩnh của lá số. Nhét trực tiếp thông tin lưu niên vào từng
`ChartPalace` sẽ làm `ChartPalace` (vốn là fact tĩnh, không đổi theo năm xem) mang dữ liệu phụ
thuộc năm ngoài ý muốn. Giữ `luu_nien` như 1 object riêng ở cấp `Chart`, chỉ tồn tại khi có
`view_year`, giữ đúng ranh giới per-chart-data (tĩnh) vs derived-by-year-data (động) đã thiết
lập từ Phase 2.

### 3.4. API Server — 2 route hiện có KHÔNG đổi chữ ký, chỉ đổi response shape

`POST /charts` và `POST /charts/rules` giữ nguyên đường dẫn + request shape (`BuildChartInput`
giờ có thêm field optional `view_year`, tương thích ngược — request cũ không có field này vẫn
hoạt động y hệt, `Chart.luu_nien` chỉ là `undefined`). Response tự động có thêm `luu_nien` (nếu
có `view_year`) và các field mới trong mỗi `ChartPalace`, không cần route mới, không cần version
API mới.

## 4. Phần B — React + Vite SPA

### 4.1. Kiến trúc & cấu trúc thư mục

```
web/
├── package.json          # React 18 + Vite, KHONG dung create-react-app
├── vite.config.ts         # dev server proxy /api -> http://localhost:3000 (Express)
├── tsconfig.json
├── index.html
└── src/
    ├── main.tsx            # entrypoint
    ├── App.tsx             # 1 component duy nhat: form + ket qua
    ├── api.ts              # fetch wrapper goi POST /charts/rules
    ├── types.ts             # copy thu cong cac type can thiet tu Chart/Rule (khong import
    │                        # truc tiep tu src/server vi web/ la package rieng, khong chung
    │                        # build voi backend — xem muc 4.2 giai thich ly do)
    └── components/
        ├── ChartForm.tsx    # form nhap: ho ten (optional, chi de hien thi)/ngay/gio/gioi tinh/lich/nam xem
        ├── PalaceGrid.tsx   # luoi 12 cung quanh vien + khoi giua
        ├── PalaceCell.tsx   # 1 o cung: chinh tinh, phu tinh 2 cot, badge, dong duoi
        └── RuleResults.tsx  # hien thi ket qua Rule Engine + conflict groups
```

**Vì sao là project riêng (`web/`), không gộp vào `src/`:** frontend build bằng Vite (bundler
riêng, output tĩnh phục vụ qua static hosting hoặc CDN sau này), backend build bằng `tsc`
(chạy trực tiếp trên Node). Gộp chung sẽ làm 2 build pipeline xung đột cấu hình TypeScript
(`tsconfig` frontend cần `jsx`, `DOM` lib; backend cần `node` types, không cần DOM). Tách package
riêng, root `package.json` không đổi.

**Vì sao `types.ts` copy tay thay vì import từ `src/`:** `web/` không phải Node package chạy
chung runtime với `src/server/` — import trực tiếp sẽ kéo theo toàn bộ dependency backend
(express, iztro...) vào bundle frontend một cách không cần thiết (chưa kể `iztro` là thư viện
tính toán nặng, không nên bundle vào browser). Copy tay các type cần thiết (`Chart`,
`ChartPalace`, `RuleEvalResult`, `ConflictGroup`) — chấp nhận trùng lặp nhỏ ở v0.1, YAGNI cho
việc dựng monorepo/shared-package phức tạp hơn.

### 4.2. Luồng dữ liệu

1. `ChartForm` thu thập: ngày sinh, giờ (time_index 0-12), giới tính, loại lịch (dương/âm), năm
   xem (optional — nếu bỏ trống, không gửi `view_year`, `luu_nien` sẽ không hiển thị).
2. Submit → `api.ts` gọi `POST /charts/rules` với `BuildChartInput` (+ `view_year` nếu có).
3. Response (`{ chart, rules_by_palace }`) lưu vào React state (`useState`, không cần
   Redux/Zustand cho 1 trang đơn giản).
4. `PalaceGrid` nhận `chart.palaces` (12 phần tử) + `rules_by_palace`, render lưới 4x4 theo bố
   cục vòng ngoài (đúng thứ tự địa chi cố định, xem mục 4.3) + khối giữa hiển thị
   `chart.metadata`/`chart.menh_than`/`chart.cuc`/`chart.ban_menh_nap_am`.
5. Mỗi `PalaceCell` nhận 1 `ChartPalace` + `rules_by_palace[branch]`, hiển thị đầy đủ theo cấu
   trúc đã xác nhận (mục 4.4) + danh sách Rule matched tại cung đó (nếu `rules_by_palace[branch]
   .matched` có phần tử `matched: true`).

### 4.3. Bố cục lưới 12 cung — vị trí cố định theo địa chi

Layout A đã chọn qua visual companion: lưới CSS Grid 4x4, khối giữa (2x2) chiếm vị trí trung
tâm. Vị trí từng địa chi trên lưới theo đúng thứ tự vòng tròn tử vi chuẩn (giống ảnh gốc, đối
chiếu qua `BRANCHES` đã có trong Chart Engine — thứ tự Tý→Hợi vòng quanh viền theo chiều đã
định sẵn, KHÔNG tự nghĩ lại thứ tự này, dùng đúng thứ tự `BRANCHES` export sẵn):

```
[Tỵ] [Ngọ] [Mùi] [Thân]
[Thìn] [———khối giữa———] [Dậu]
[Mão] [———khối giữa———] [Tuất]
[Dần] [Sửu] [Tý] [Hợi]
```

Mapping cụ thể sang CSS Grid `grid-column`/`grid-row` viết chi tiết trong implementation plan
(không phải quyết định thiết kế, là chi tiết code).

### 4.4. Cấu trúc hiển thị 1 ô cung — đã xác nhận qua visual companion (đối chiếu ảnh gốc)

```
┌─────────────────────────────┐
│ [Can+Chi cung]  [TÊN CUNG]  [tuổi Đại Vận] │  ← palace_stem+branch, palace_name, decadal.range[0]
│ -[Ngũ hành cung]                            │  ← branch_element
│ +[Chính tinh 1] ([độ sáng])                 │  ← major_stars[], strength
│ +[Chính tinh 2] ([độ sáng])  (nếu có)       │
│ [cát 1]         [sát/khác 1]                │  ← lưới 2 cột: minor_stars (type=soft) trái,
│ [cát 2]         [sát/khác 2]                │     minor_stars (type=tough) phải (adjective_stars
│                                              │     hiển thị RIÊNG, xem dòng dưới — không đoán cát/hung)
│ Tạp diệu: [adjective_stars, liệt kê phẳng]   │  ← KHÔNG chia cột — iztro không có field type
│ [Badge Tuần/Triệt nếu có]                    │  ← adjective_stars chứa TUAN_KHONG/TRIET_LO
│ ĐV.[tên cung Đại Vận]  [Tràng Sinh]           │
│ Bác Sỹ: [boshi]  Tướng Tiền: [jiangqian]  Tuế Tiền: [suiqian] │  ← liệt kê riêng, KHÔNG chia cột
│ LN.[tên cung Lưu Niên nếu có]                │
└─────────────────────────────┘
```

**Quy tắc chia 2 cột phụ tinh — CHỈ áp dụng cho `minor_stars`** (đã xác nhận qua khảo sát dữ
liệu thật): dùng field `type` có sẵn trên mỗi sao từ `iztro` (`'soft'` = cát tinh → cột trái,
`'tough'` = sát tinh → cột phải). **Quyết định (brainstorm 2026-08-18): KHÔNG mở rộng quy tắc
2 cột này sang `adjective_stars` hay 4 vòng 12 thần** (`truong_sinh`/`boshi`/`jiangqian`/
`suiqian`) — `iztro` không cung cấp field `type` cho các sao này, và tự biên soạn bảng phân
loại cát/hung cho 36 tên sao (12 sao × 3 vòng) không có nguồn đối chiếu là rủi ro đoán sai, đúng
loại lỗi dự án đã nhiều lần cảnh giác. `adjective_stars` hiển thị thành 1 danh sách phẳng riêng
(không chia cột); 3 vòng `boshi`/`jiangqian`/`suiqian` hiển thị thành nhãn có tên vòng đi kèm,
mỗi vòng 1 dòng — người xem tự đối chiếu ý nghĩa cát/hung nếu cần, UI không tự gán nhãn.

### 4.5. Khối trung tâm

Hiển thị đầy đủ theo đúng ảnh gốc (đã xác nhận qua mockup, không cần đổi):
họ tên (field riêng trong `ChartForm`, KHÔNG gửi lên API — `Chart` không có khái niệm "tên
