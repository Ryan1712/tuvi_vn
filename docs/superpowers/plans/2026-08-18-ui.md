# UI (Phase 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend Chart Data Shape with the four 12-position auxiliary star cycles, branch
element, and optional Lưu Niên; then build a React + Vite single-page app that renders a full
12-palace chart (matching tuvi.vn's information density) plus Rule Engine results, consuming
the existing API server.

**Architecture:** Two halves executed in order. Tasks 1-4 extend `src/chart/` (adapter reads 4
new `iztro` fields already available but unmapped, plus a static branch→element lookup and an
optional `astrolabe.horoscope()` call) with matching test coverage — this must land first since
the frontend depends on the extended `Chart` shape. Tasks 5-9 scaffold a Vite React app in
`web/` that fetches from the existing `POST /charts/rules` endpoint and renders the palace grid.

**Tech Stack:** Backend: TypeScript ESM, Vitest (unchanged — extends existing `src/chart/`).
Frontend: React 19.2.8, Vite 8.2.1, TypeScript 6.0.2 (Vite's own scaffold pins this
independently of the backend's `typescript@^5.9.3` — separate package, no conflict), no state
library, no CSS framework.

## Global Constraints

- Never fabricate a value `iztro` doesn't provide. The one unidentified image field ("Th.1") is
  NOT displayed anywhere in this plan — do not add it, do not guess at it.
- Never force UI data to match the tuvi.vn reference image when `iztro`'s real output differs
  (e.g. Thiên Khôi's palace position). Display exactly what `iztro`/the existing Chart Engine
  computes.
- Do NOT invent an auspicious/inauspicious column split for `boshi12`/`jiangqian12`/`suiqian12`
  — `iztro` provides no `type` field for these three cycles (unlike `minorStars`, which has
  `soft`/`tough`). They render as flat, labeled lists, never split into two columns.
- The four new 12-position-cycle fields (`truong_sinh`, `boshi`, `jiangqian`, `suiqian`) are
  stored as raw Vietnamese strings from `iztro`, NOT passed through `starIdFromVi` — they are
  cycle *positions/states*, not stars used for Rule Engine matching, and several names collide
  across cycles with different meanings (e.g. "Đại Hao" appears in both `boshi12` and
  `suiqian12` meaning different things) — forcing them through the star_id table would conflate
  those meanings.
- `Chart.luu_nien` is optional and populated ONLY when `BuildChartInput.view_year` is provided.
  It is never a required field of `Chart` — Lưu Niên is year-dependent data, not a static chart
  fact, consistent with `LuckCycles`' existing exclusion of `luu_nien` from `dai_van`/`tieu_van`.
- Do not modify `POST /charts` or `POST /charts/rules`'s URL paths or request shape beyond
  adding the optional `view_year` field — both stay backward compatible with existing callers.
- Frontend has NO automated tests at this stage (per build spec section 14 — UI only needs to
  be information-complete, not test-covered yet). Verify by running the dev server for real.
- No CSS framework, no animation, no responsive polish, no routing library — one page, one
  component tree, inline styles or a single plain CSS file are enough.
- `web/` is a separate npm package from the project root — do not import backend source
  (`src/chart/`, `src/rule/`) directly into `web/`; copy the handful of needed types by hand
  into `web/src/types.ts` instead (avoids bundling `iztro`/`express` into the browser build).

**Why `MinorStar` needs a `type` field:** the UI design (design doc section 4.4) splits
`minor_stars` into two columns using `iztro`'s own auspicious/inauspicious classification. That
classification exists on `iztro`'s raw star objects (`StarType`) but was never carried into
`MinorStar` when Chart Engine was first built (Phase 2 only needed `star_id`/`strength` at the
time). Verified directly against real `iztro` output during planning: `StarType` has exactly 8
values — `'major' | 'soft' | 'tough' | 'adjective' | 'flower' | 'helper' | 'lucun' | 'tianma'` —
and all 8 were observed occurring across the Phạm Duy chart's 12 palaces. `major_stars` always
has `type: 'major'` (not useful to carry) and `adjective_stars` always has `type: 'adjective'`
(also not useful — already a separate field), but `minor_stars` genuinely varies across all 6
remaining values, which is exactly the data the UI needs.

/**
 * Luu Nien cho 1 nam xem cu the. `iztro.astrolabe.horoscope(dateStr, timeIndex).yearly`
 * co `palaceNames[i]`/`stars[i]` DUNG CHUNG index voi `astrolabe.palaces[i]` (theo vi
 * tri, khong phai theo branch) — da xac minh thuc te trong luc lap ke hoach.
 */
function adaptLuuNien(astrolabe: IFunctionalAstrolabe, viewYear: string): LuuNien {
  const horoscope = astrolabe.horoscope(viewYear, 0);
  const yearly = horoscope.yearly;
  const year = Number.parseInt(viewYear.split('-')[0] ?? '', 10);
  const palaces: LuuNienPalace[] = astrolabe.palaces.map((p, i) => ({
    branch: branchFromVi(p.earthlyBranch),
    palace_name: yearly.palaceNames[i] ?? '',
    stars: (yearly.stars?.[i] ?? []).map((s) => ({ star_id: starIdFromVi(s.name) })),
  }));
  return {
    year,
    heavenly_stem: yearly.heavenlyStem,
    earthly_branch: yearly.earthlyBranch,
    mutagen: [...yearly.mutagen],
    palaces,
  };
}

export async function fetchChartWithRules(
  input: BuildChartInput,
): Promise<ChartRulesResponse> {
  const res = await fetch('/api/charts/rules', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(input),
  });
  if (!res.ok) {

  }
  return (await res.json()) as ChartRulesResponse;
}

import { useState } from 'react';
import { ChartForm } from './components/ChartForm';
import { PalaceGrid } from './components/PalaceGrid';
import { fetchChartWithRules } from './api';
import type { BuildChartInput, ChartRulesResponse } from './types';

function App() {
  const [data, setData] = useState<ChartRulesResponse | null>(null);
  const [displayName, setDisplayName] = useState('');
  const [error, setError] = useState<string | null>(null);
  const [loading, setLoading] = useState(false);

    setLoading(true);
    setError(null);
    try {
      const result = await fetchChartWithRules(input);
      setData(result);
      setDisplayName(name);
    } catch (e) {
      setError(e instanceof Error ? e.message : 'Lỗi không xác định');
      setData(null);
    } finally {
      setLoading(false);
    }
  }

  return (

      <h1>Tử Vi</h1>
      <ChartForm onSubmit={handleSubmit} />
      {loading && <p>Đang tính...</p>}
      {error && <p className="error">Lỗi: {error}</p>}
